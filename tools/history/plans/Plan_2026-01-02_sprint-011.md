## 1. Alcance y objetivos

### Objetivo funcional (no negociable)
Mantener el comportamiento observable actual del VSIX:
- ToolWindow “Agente IA Local”: ejecutar **Run**, enviar prompt al backend (LM Studio / JAN stub), renderizar respuesta (Markdown/JSON/plain), y persistir logs en `%LOCALAPPDATA%\AgenteIALocal\logs\AgenteIALocal.log`.
- Logging homogéneo: **toda** persistencia debe estar normalizada por `LogEntryTextFormatter` (formato `ts=... lvl=... corr=... eid=... msg=...`).

### Objetivo técnico
1) Eliminar código **no usado** (métodos/clases/proyectos/subsistemas) con verificación exhaustiva (compilación + smoke test).  
2) Reducir acoplamiento y violaciones SRP/SOLID, preparando un **gran refactor por fases** (sprints cortos, ≤ 5 tareas).  
3) Consolidar la arquitectura (Clean Architecture/Onion) minimizando dependencias cruzadas y duplicación funcional.

### Restricciones operativas (Reglas.md)
- Trabajo por pasos atómicos, con verificación por paso, y commit entre tareas.
- Copilot no debe modificar archivos prohibidos (`*.vsix`, `*.vsct`, `*.vsixmanifest`, `*.csproj`, `*.sln`).  
  Nota: el humano puede hacerlo cuando sea estrictamente necesario.

## 3. Hallazgos (exhaustivos por categorías)

### 3.1 Clean Architecture (dependencias y límites)
**En general** la direccionalidad principal es correcta (Core no depende de capas externas).  
Problemas concretos detectados:
- **Dependencias cruzadas por assets**: `AgenteIALocal.Application.csproj` y `AgenteIALocal.Infrastructure.csproj` incluyen `..\AgenteIALocalVSIX\favicon-128.png` como `PackageIcon`. Esto acopla librerías a un asset del host VSIX. Impacto: acoplamiento innecesario y fricción en refactors/packaging.
- **Duplicación de subsistemas de “settings”**:
  - `AgenteIALocalVSIX/AgentSettingsStore.cs` (JSON en LocalAppData) está **usado** por ToolWindow y ConfigWindow.
  - `AgenteIALocal.Core/Settings/*` + `AgenteIALocalVSIX/Settings/*` + `ToolWindows/AgenteIALocalConfigViewModel.cs` aparentan ser un camino alternativo **no cableado** (sin referencias en el código/ XAML).
  Resultado: dos formas de resolver el mismo problema (configuración) sin una decisión clara.

### 3.2 SOLID / SRP (responsabilidad única y acoplamiento)
- **SRP severo**: `AgenteIALocalControl.xaml.cs` concentra UI + networking + parsing + render + normalización + logging + persistencia. Esto incrementa el riesgo de regresión y dificulta testeo.
- **Networking dentro de UI**:
  - `FetchModelsFromBaseUrlAsync` (ToolWindow) y lógica análoga en `AgenteIALocalConfigWindow.xaml.cs` duplican llamadas HTTP y parsing.
  - Problema adicional: ausencia de abstracción para facilitar tests/mocks.
- **Acoplamiento a System.IO** en varios puntos (host y sinks) con `File.AppendAllText` y `catch` silencioso.

### 3.3 HTTP / Tipado / Robustez
- `LmStudioClient` usa `HttpWebRequest` + `Task.Run(...)` (async sobre sync IO) + JSON armado a mano (StringBuilder):
  - Riesgos: payload frágil, errores difíciles de rastrear, timeouts/cancelación poco claros, overhead y potencial de deadlocks.
  - Desalineación con el requisito: **HttpClientFactory**.
- Parsing de respuesta se hace por búsqueda de cadenas/índices; debería pasar a un modelo tipado (System.Text.Json / JsonDocument).

### 3.4 Logging (homogeneidad y confiabilidad)
- Se avanzó en unificación a `LogEntryTextFormatter`; sin embargo:
  - Persistencia a disco aún depende de sinks que hacen `File.AppendAllText` con `catch { }` (silencioso). Esto es defensivo para no romper la extensión, pero resta observabilidad.
  - Existen paths en UI/Package que formatean LogEntry y escriben (mejor que legacy), pero el objetivo final debería ser: **un solo punto de persistencia** (sink) y el resto emite `LogEntry`.

### 3.5 Código duplicado / subsistemas redundantes
- Duplicación funcional: “Fetch models” en ToolWindow y ConfigWindow.
- Duplicación de arquitectura: “AI provider”/“Agent planner” legacy vs nuevo pipeline `IAgentClient` + `AgentService`.
- Duplicación de settings: Core.Settings + VSIX.Settings vs AgentSettingsStore.

### 3.6 Código potencialmente muerto (sin uso actual)
Estos directorios contienen código que **no aparece referenciado fuera del propio árbol** (búsqueda literal en repo), y representan alto candidato a eliminación (con verificación por build + smoke test):

**A3. Definir “lista de exclusión” (NO borrar)**
- Entrada: VSIX entrypoints (Package, ToolWindow, Commands, manifest-related) y clases referenciadas por XAML.

### Fase B — Limpieza segura (dead code + warnings) (1–2 sprints)
**B1. Eliminar warnings triviales (CS0168/CS0219/etc.)**
- Objetivo: reducir ruido y facilitar refactor posterior.

**B2. Eliminar subsistemas claramente no usados**
- Propuesta: remover `Infrastructure/AI`, `Infrastructure/Agent`, `Core/Interfaces/AI`, `Core/Interfaces/Agent`, `Core/Models/AI` (si la verificación confirma 0 uso).
- Riesgo: medio (por posibles referencias futuras). Mitigación: extracción por commits pequeños + verificación con smoke tests.

**B3. Eliminar Options/Settings alternativos si no están cableados**
- Si `AgenteIALocalVSIX/Options` y `AgenteIALocalVSIX/Settings` no se usan: eliminar.
- Nota: esto puede requerir editar `.csproj` (tarea humana) si hay includes explícitos.

### Fase C — Consolidación de configuración (1 sprint)
**C1. Elegir una fuente de settings**
Recomendación: mantener `AgentSettingsStore` (LocalAppData JSON) como source of truth (por uso actual).
- Acciones: eliminar o archivar el camino alternativo `Core.Settings` + `VsWritableSettingsStoreAgentSettingsProvider` + `AgenteIALocalConfigViewModel` si efectivamente no se utiliza.
- Beneficio: elimina duplicación y reduce acoplamiento conceptual.

### Fase D — SRP en UI: extraer servicios internos del VSIX (2–3 sprints)
**D1. Extract: “Model Catalog Fetch”**
- Crear `IVsixModelCatalogClient` (VSIX interno) y mover allí:
  - `FetchModelsFromBaseUrlAsync` + parseo + manejo de errores.
- ToolWindow y ConfigWindow sólo orquestan UI.

**D2. Extract: render + normalización**
- Extraer `JsonResponseRenderer`/`MarkdownResponseRenderer` a archivos propios.
- Mantener `ResponseNormalizer` como componente puro (idealmente sin dependencia VSIX, solo strings + JSON parsing).

**D3. Reducir `catch { }` vacíos**
- Donde aplique, reemplazar con logging Verbose/Error (sin romper UI).
- Mantener comportamiento defensivo en sinks (logging nunca debe romper VSIX).

### Fase E — Refactor de clientes (HTTP + tipado + resiliencia) (2–4 sprints)
**E1. LmStudioClient: HttpClient + System.Text.Json**
- Reemplazar `HttpWebRequest` + `Task.Run` por `HttpClient.SendAsync`.
- Payload tipado:
  - Request DTO: `model`, `messages[]`, etc.
  - Response DTO: extraer `choices[0].message.content`.
- Timeouts y CancellationToken end-to-end.

**E2. HttpClientFactory (sin contenedor DI)**
- Introducir una fábrica simple en Infrastructure, inicializada por VSIX composition.
- Mantener extensibilidad para futuros providers.

### Fase F — Calidad y gobierno (continuo)
**F1. Analizadores y reglas**
- Activar analyzers y/o StyleCop (cambio humano en `.csproj`).
- Política: warnings críticos como error en CI (cuando esté listo).

**F2. Tests mínimos (sin romper VSIX)**
- Unit tests para:
  - `ResponseNormalizer`
  - parser de respuesta LM Studio
  - construcción de request
- Enfocados a “no regresión”.

## 6. Scripts de discovery (PowerShell) — ejecutar sólo cuando corresponda

> Importante: estos scripts son para generar evidencia, NO para borrar automáticamente.

### D-PS1: generar tokens XAML + compile items
```powershell
# Desde la raíz del repo
$ErrorActionPreference = "Stop"

# 1) Tokens XAML (bindings/handlers)
Get-ChildItem -Path .\src -Recurse -File -Include *.xaml |
  ForEach-Object {
    $x = Get-Content $_.FullName -Raw
    [regex]::Matches($x, "[A-Za-z_][A-Za-z0-9_]*") | ForEach-Object Value
  } |
  Sort-Object -Unique |
  Set-Content .\deadcode.xamltokens.txt -Encoding UTF8

# 2) Compile Includes explícitos (para csproj clásicos)
$csproj = ".\src\AgenteIALocalVSIX\AgenteIALocalVSIX.csproj"
[xml]$xml = Get-Content $csproj
$items = @()
$xml.Project.ItemGroup.Compile | ForEach-Object {
  if ($_.Include) { $items += $_.Include }
}
$items | ConvertTo-Json | Set-Content .\deadcode.compileitems.json -Encoding UTF8
```

### D-PS2: reporte de candidatos dead-code por “ocurrencias = 1”
```powershell
# Heurística: un tipo declarado cuyo nombre aparece 1 sola vez suele ser no usado.
# Requiere revisión manual (XAML/reflection/MEF).
$ErrorActionPreference = "Stop"

$csFiles = Get-ChildItem .\src -Recurse -File -Include *.cs
$content = $csFiles | ForEach-Object { Get-Content $_.FullName -Raw }

# Extrae nombres de clases/interfaces/enum (simplificado)
$decl = @()
foreach ($f in $csFiles) {
  $t = Get-Content $f.FullName -Raw
  [regex]::Matches($t, "\b(class|interface|enum|struct)\s+([A-Za-z_][A-Za-z0-9_]*)") | ForEach-Object {
    $decl += [pscustomobject]@{ File=$f.FullName; Kind=$_.Groups[1].Value; Name=$_.Groups[2].Value }
  }
}

# Cuenta ocurrencias del nombre en el repo (texto)
$allText = ($content -join "`n")
$report = foreach ($d in $decl) {
  $count = ([regex]::Matches($allText, "\b" + [regex]::Escape($d.Name) + "\b")).Count
  [pscustomobject]@{ Name=$d.Name; Kind=$d.Kind; DeclFile=$d.File; Occurrences=$count }
} | Sort-Object Occurrences, Name

$report | ConvertTo-Json -Depth 4 | Set-Content .\deadcode.occurrences.json -Encoding UTF8
```
